## Secuencia para la intervención autorizada

1. Confirmar por escrito que la autorización cubre **solo Staging**, las dos migraciones y el borrado de cuentas sintéticas creadas explícitamente para este ensayo. Acordar responsable, horario y condiciones de pausa. Registrar el SHA de código y el identificador del proyecto antes de abrir el cliente SQL. Verificar versiones de Auth/Storage/Edge y ruta de acceso de la app, particularmente si difieren del ensayo local.
2. Obtener el respaldo disponible antes del cambio y comprobar su alcance. Guardar fuera de Git con permisos de propietario las definiciones, propietario, `proacl` y `proconfig` de los tres detectores privados y la configuración de RLS, triggers y grants de las tablas que toca UGC. Un respaldo SQL no incluye los bytes de Storage. Preservar inventario de objetos y copias solo del conjunto sintético que se va a ensayar. Si el procedimiento de respaldo o reversión no es viable, hacer el ensayo en un entorno desechable autorizado.
3. Seleccionar explícitamente Staging en el CLI fijado y ejecutar el dry run de migraciones con su conexión aprobada. Debe listar exclusivamente, en este orden, `20261119231916_reconocer_cuota_rutas_eliminacion.sql` y `20261120034446_controles_ugc_cercly.sql`. La primera reemplaza un detector y admite solo la FK exacta de la cuota. La segunda crea UGC y amplía detectores revisados, sin cambiar esa migración anterior. Detenerse ante cualquier diferencia de historial, ACL, definición o migración extra. Después de aprobar el plan aplicar únicamente ese lote por el procedimiento de migración registrado. No copiar datos ni credenciales de Production.
4. Repetir la comprobación de metadatos con los resultados esperados: cuota reconocida, UUID inexistente sin bloqueo, esquema y RPC UGC presentes. Confirmar buckets privados, RLS restrictivo en filas de catálogo, permisos mínimos de RPC, configuración del gateway y `verify_jwt` de `eliminar-cuenta`. La FAQ web y la APK no instalan el backend.
5. Crear un conjunto nuevo identificado con un prefijo de ensayo, con usuarios sintéticos separados para propietario, lector denunciante, observador, moderador y cuenta descartable. Marcar el UUID de cada identidad y la lista de objetos de Storage. Probar bajo permisos de cada rol y vía el gateway real. Reservar credenciales en un archivo local privado temporal. El arnés existente de HTTP restringe el destino a loopback y **no se adapta retirando sus guardas**.

| ID | Ejecutar con los sujetos sintéticos | Evidencia para aprobar |

| S01 | Intentar crear foto/promoción antes de aceptar, cancelar, aceptar texto y huella, repetir con la versión correcta | Rechazo del servidor antes de aceptar, aceptación con hora y misma huella. | S02 | Otra cuenta aceptada intenta escribir en el negocio ajeno y un visitante lee catálogo visible | Escritura rechazada, catálogo autorizado disponible, acceso directo a buckets privados denegado sin firma. |
| S03 | Denunciar ficha, foto, promoción y responsable. Repetir, bloquear y volver a iniciar sesión | Denuncias propias visibles sin exponer ajenas. Duplicado no crea otro caso. Bloqueo persistente en Explore, mapa, promociones y nuevas firmas de imagen. El observador no queda afectado. |
| S04 | Intentar moderar con rol cliente y como moderador independiente. Retirar foto/promoción y consultar como visitante | Cliente rechazado. Moderador autorizado registra transición y motivo. El elemento retirado desaparece de catálogo y las firmas nuevas fallan. Preservar prueba de que los objetos ajenos continúan intactos. |
| S05 | Probar eliminación desde la app con cuenta simple que tiene preferencias, cuota sintética, aceptación, bloqueo propio y sesión | Handler alojado confirma eliminación. Ausencia de Auth, perfil, sesiones, refresh, preferencias, cuota, aceptación y bloqueo. JWT anterior no puede recrear datos sensibles. Revisar que HTTP sin sesión es 401 y no altera datos. |
| S06 | Probar cuenta titular de una foto propia y cuenta con negocio, promoción o datos compartidos | La revisión conserva objetos compartidos hasta decisión. Cuando corresponda, retirar solo el objeto sintético por Storage API y comprobar bytes inaccesibles, después ejecutar el procedimiento autorizado. Confirmar inventario y hashes ajenos intactos. |
| S07 | Solicitar eliminación de la cuenta que creó una denuncia aunque ya se resolvió | Riesgo confirmado en código. Ambos detectores consideran la participación en denuncias y el flujo revisado comprueba el bloqueo externo. Ver una solicitud pendiente no basta. Antes de incluir usuarios reales, demostrar una resolución autorizada con minimización de identidad y detalle personal sin borrar la actuación ajena. Si el caso sigue atascado, necesita una decisión de conservación y el cambio local correspondiente. |
| S08 | Mecanismo externo desde `/eliminar-cuenta` con cuenta sintética y autorización específica para el envío | Verificar recepción, titularidad y confirmación posterior. Capturar horas, estados y respuesta saneada. El enlace de correo y la vista del formulario por sí solos no prueban la atención. |

Resumen del ensayo: SHA fuente, hashes de migraciones, ref Staging, resultado PASS/FAIL por ID, dispositivo/versiones de servicios, códigos HTTP y SQLSTATE, huellas de identificadores y objetos ajenos antes/después, incidencias y responsable. No incluir correos, JWT, contraseñas, identificadores reales ni detalle personal de denuncias.

**Reversión.** Ambas migraciones usan transacciones, por lo que un error durante la aplicación revierte esa migración. Después del commit, el reemplazo de detector se puede revertir con la definición y ACL previas solo si el impacto y sus dependencias fueron revisados, porque reintroduce el bloqueo conocido. Tras registrar aceptaciones/denuncias, retirar el esquema UGC perdería evidencias. Pausar el ensayo y preparar corrección hacia adelante o restaurar exclusivamente un entorno desechable. Un borrado de Auth/Storage sintético es esperado, y restaurar un ambiente compartido nunca es un procedimiento de reversión de rutina.

## Lista para el HONOR

ADB no detectó dispositivos en la revisión. Instalar primero el APK `.staging` del SHA futuro validado, después de S01–S04. Para crearlo, usar `flutter build apk --debug --no-pub --dart-define-from-file=<ruta privada Staging>`, con `CERCLY_STAGING=true`, URL Staging y su clave publicable. Verificar paquete `com.cercly.cercly.staging` y etiqueta Cercly STAGING. Con depuración USB habilitada, verificar `adb devices -l` e instalar ese APK con `adb install -r <apk>`. Registrar modelo, Android/MagicOS, variante, código, SHA y hora. La variante Staging tiene capacidades de prueba distintas. Confirmar la configuración de Radar y permisos otra vez desde la instalación generada por Play en cuanto el track esté autorizado.
